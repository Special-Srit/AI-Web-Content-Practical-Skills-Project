1. 과다 사용 목록 — 주제: 한눈에 보이는 일반성의 이유와 가능한 구제 방식

스캔 메모: 여기서 “과다 사용”은 통계 순위가 아니라 쇼케이스 갤러리, 국비 후기, 초급 과정 예시를 바탕으로 한 포지셔닝 판단이다. [내 판단]

- 투두·캘린더: 추가/수정/삭제/필터/날짜 UI가 초급 CRUD로 즉시 인식된다. 부트캠프 쇼케이스에도 플래너와 캘린더 기능이 자주 등장한다. [출처: [부트캠프 교육생 결과물](https://nbcamp-blog.oopy.io/ccff183c-94e6-4c80-9f4b-d0c33d9b84e5)] 구제: “직업계고 실습 전 준비물·안전 체크”처럼 구체적인 사용자 순간에 성찰이나 위험 처리를 더하는 경우에만 가능하며, 그 외에는 피한다. [내 판단]

- 날씨 앱: 대체로 API fetch, 날씨 카드, 아이콘, 예보 탭으로 끝나 구현 이야기가 익숙하다. [내 판단] 구제: 좁은 대상의 의사결정 도구로 만들기 — “등하교·실습복장 위험 알림”과 fallback 데이터, 단위 처리, 설명 가능한 경고 규칙을 결합한다. [내 판단]

- 계산기: 기본 산술은 입력 이벤트와 연산자 이상을 거의 보여 주지 못한다. [내 판단] 구제: 레시피 배율 조정이나 아르바이트 근무 수당처럼 전제 조건이 보이는 도메인별 계산으로 만든다. 일반 계산기는 구제 방법이 없다. [내 판단]

- MBTI·성격테스트: 퀴즈 → 네 글자 결과 → 공유 카드 흐름은 학생 프로젝트의 가장 뚜렷한 클리셰 중 하나다. MBTI는 한국에서 반복 사용되는 콘텐츠 카테고리이기도 하다. [출처: [Velog MBTI tag](https://velog.io/tags/MBTI)] 구제: 성격 라벨 대신 투명한 시나리오 기반 의사결정 도구로 바꾼다. 단순 MBTI 클론은 피한다. [내 판단]

- 영화·도서 검색: 검색 API, 카드, 상세 페이지, 좋아요, 필터는 남의 데이터를 감싼 흔한 형태다. [내 판단] 구제: 검색 자체가 아니라 “20분 안에 읽을 책”, “혼자 보기 불편하지 않은 영화”처럼 의사결정 문제를 좁히고 선별 이유를 제공한다. [내 판단]

- 가계부·소비관리: 폼 입력, 카테고리 합계, 차트, localStorage는 표준적인 연습 프로젝트 소재다. [내 판단] 구제: 청소년 충동구매, 구독 누수, “후회 소비” 성찰처럼 특정 행동을 겨냥하고 전후 의사결정 루프를 보여 준다. [내 판단]

- 방문자 카운터·방명록·게시판: 전형적인 JSP/Oracle 및 국비 CRUD 연습과 강하게 연결되는 주제다. 한 국비 후기는 CRUD 게시판 제작을 기본 역량으로 명시하고, 다른 후기는 영화 예매 최종 프로젝트를 소개한다. [출처: [국비 웹개발 후기](https://newehblog.tistory.com/51)] 가짜 로컬 전용 공개 카운터로는 구제할 수 없으므로 피한다. [내 판단]

- 포트폴리오 사이트: 개인 프로필, 기술, 프로젝트 카드, 연락처 섹션은 대체로 제품보다 자기소개로 읽힌다. 포트폴리오 피드백도 반복되는 학원식 형식이 지원자별 강점을 보기 어렵게 만든다고 경고한다. [출처: [UX 포트폴리오 매거진](https://brunch.co.kr/magazine/ux-portfolio)] 구제: 또 하나의 포트폴리오 홈이 아니라 한 가지 기술이나 프로세스를 증명하는 인터랙티브 결과물로 만든다. [내 판단]

- 유명 서비스 클론코딩: Watcha, Kakao, 쇼핑몰, 배달 앱, SNS의 시각적 모방은 독립적인 문제 설정보다 복사와 스타일링을 보여 준다. 한국 프론트엔드 쇼케이스에도 Watcha와 Kakao Friends-shop 클론이 흔한 미니 프로젝트 형식으로 소개된다. [출처: [제로베이스 미니 프로젝트 발표](https://zero-base.co.kr/event/media_nklcb_contents_4)] 구제: 상호작용 하나를 재현한 뒤 접근성, 성능, UX 개선을 기록한다. 전체 클론은 여기서 막다른 길이다. [내 판단]

- 쇼핑몰·이커머스: 상품 목록, 장바구니, 주문, 로그인은 전형적인 국비 최종 프로젝트 형태다. 한 국비 수료 후기는 쇼핑몰을 자유 주제 프로젝트로 소개한다. [출처: [국비 수료 후기](https://drg2524.tistory.com/137)] 고정 로컬 데이터 기반의 좁은 비교·재고 의사결정 도구로만 구제할 수 있다. 전체 쇼핑몰 범위는 7일에 너무 넓다. [내 판단]

- 여행·맛집·지도 플래너: 부트캠프 갤러리에는 여행 코스, 지도, 숙소, 음식점, 플래너 서비스가 많이 있다. [출처: [부트캠프 교육생 결과물](https://nbcamp-blog.oopy.io/ccff183c-94e6-4c80-9f4b-d0c33d9b84e5)] 예산, 도보 거리, 접근성, 악천후 fallback처럼 실제 트레이드오프가 있는 명확히 제한된 지역 시나리오로 만든다. [내 판단]

- 채용공고·커뮤니티·SNS: 피드, 검색, 좋아요, 게시물, 프로필은 흔한 제품 껍데기지만 localStorage만으로는 신뢰할 만한 다중 사용자 동작을 제공할 수 없다. [내 판단] 개인 의사결정 보조 도구나 오프라인 포트폴리오 결과물로 구제하며, 실제 소셜 서비스인 척하지 않는다. [내 판단]

2. 관심을 얻는 차별화 패턴

- 기능 목록이 아니라 관찰 가능한 사용자 문제 하나에서 시작한다. 눈에 띄는 쇼케이스 프로젝트는 대체로 반려동물 병원비 비교, 고양이 돌봄 교환, 채용 필터링, 여행 코스 계획처럼 좁은 대상과 상황을 명시한다. [출처: [부트캠프 교육생 결과물](https://nbcamp-blog.oopy.io/ccff183c-94e6-4c80-9f4b-d0c33d9b84e5)] 이 프로젝트에서 “학생”은 여전히 넓고, “실습을 준비하는 직업계고 학생”이 더 강하다. [내 판단]

- 완성된 의사결정 루프 하나를 만든다. 입력 → 평가 → 선택 → 저장/검토가 서로 무관한 페이지 5개보다 기억에 남는다. 포트폴리오 피드백은 명확한 배경, 문제 정의, 목표, 해결책, 결과를 반복해서 선호한다. [출처: [포트폴리오 프로젝트 내용 구성](https://brunch.co.kr/%40%401561/31)] [내 판단]

- 실제 반 친구 몇 명에게 테스트하고 무엇이 바뀌었는지 보여 준다. 7일 프로젝트라면 짧은 과업 테스트 3회, 오류 수, 완료 시간, 인용문 정도면 충분하며 통계적 타당성까지 필요하지 않다. 포트폴리오 가이드에서도 사용자 피드백 기반 개선을 반복해서 강조한다. [출처: [결과해석과 유저 피드백](https://brunch.co.kr/%40%402hV3/256)] [내 판단]

- 제한된 데이터를 디자인 선택으로 다룬다. 명확한 분류와 설명이 있는 작고 선별된 한국어 데이터셋이 얇은 API 래퍼보다 강하다. API를 사용한다면 loading, empty, stale, failure, fallback 상태를 보여 준다. [내 판단]

- localStorage를 제품 약속의 일부로 만든다. “비공개, 오프라인, 계정 불필요”는 개인 체크리스트, 성찰 도구, 시뮬레이터, 저장된 추천 목록에는 설득력이 있지만 공개 게시판이나 실제 방문자 카운터에는 설득력이 없다. [내 판단]

- 어색한 상태를 다듬는다. 빈 결과, 중복 입력, 잘못된 한국어 입력, 모바일 레이아웃, 키보드 탐색, 초기화 동작, 새로고침 후 유지 여부는 작지만 눈에 보이는 품질 신호다. [내 판단]

- 기술이 아니라 결정을 설명한다. 포트폴리오 심사자는 얕은 문제 정의와 “기능이 없다”에서 곧바로 “추가했다”로 뛰는 해결책을 비판한다. [출처: [문제 해결형 포트폴리오의 맹점](https://brunch.co.kr/%40%40bpd/56)] 짧은 결정 기록이 HTML/CSS/JS 나열보다 기억에 남을 수 있다. [내 판단]

- 발표 자체를 재현 가능한 이야기로 만든다: 사용자 문제, 라이브 시나리오 하나, 발견한 실패 하나, 수정 하나, 최종 결과. 프로젝트 평가 사례는 문제 명확성, 데모 신뢰성, 스토리텔링, 역할 분담, Git 활동, README, 회고를 명시적으로 평가한다. [출처: [프로젝트 평가기준](https://www.dongseo.ac.kr/kr/index.php?idx=102293&mode=fdn&num=1&pCode=MN2000197)] [내 판단]

3. 2인 분업

깔끔한 분담:

- 합의한 하나의 데이터 형태를 사용하는 두 개의 세로 흐름: A는 탐색/입력/필터/저장, B는 상세/결과/설명/검토를 맡는다. 첫날 필드와 샘플 데이터를 고정한 경우에만 가능하다. [내 판단]

- “기록”과 “해석”: 한 사람은 폼, 검증, localStorage, 초기화, 다른 사람은 요약, 점수, 차트, 결과 설명을 맡는다. 저장 객체 형식에 합의하면 독립적으로 작업할 수 있다. [내 판단]

- “시나리오 A”와 “시나리오 B”: 같은 컴포넌트를 사용하는 두 개의 병렬 사용자 여정. 예를 들어 평상일 계획과 긴급일 계획으로 나눈다. 한 사람이 모든 로직을 소유하는 상황을 피할 수 있다. [내 판단]

- 공통 셸과 독립 기능 모듈: 한 사람은 레이아웃, 내비게이션, 반응형 규칙, 재사용 카드, 다른 사람은 완성된 인터랙티브 기능 하나를 맡는다. 셸을 일찍 끝내지 않으면 두 번째 사람이 막힌다. [내 판단]

무너지는 분담:

- 정적 포트폴리오 또는 랜딩 페이지: 의미 있는 결정이 거의 모두 시각 영역에 집중되므로 한 사람은 레이아웃 담당이 되고 다른 사람은 문구나 이미지만 제공하게 된다. [내 판단]

- 일반 계산기, 날씨 카드, 작은 퀴즈: 핵심 JavaScript가 두 개의 의미 있는 작업 흐름을 만들기에는 너무 작다. 한 사람은 로직을 쓰고 다른 사람은 꾸미게 된다. [내 판단]

- 전체 클론코딩: 시각적 일관성이 단일 게이트키퍼를 만든다. 간격, 컴포넌트, 상호작용이 클론과 맞아야 하므로 두 번째 사람의 작업이 계속 다시 작성된다. [내 판단]

- 백엔드 없는 게시판, 채팅, SNS, 쇼핑몰: “진짜” 상태 모델이 불명확해 한 사람은 localStorage와 통합을 맡고 다른 사람은 연결되지 않은 화면을 만들게 된다. [내 판단]

- 지도/여행/API 중심 프로젝트: 한 사람이 API 키, 응답 형태, 오류 처리를 통제하므로 다른 사람은 독립 테스트를 할 수 없고 통합을 기다리게 된다. [내 판단]

- 범위가 넓은 CRUD 대시보드: 두 사람이 같은 자료 구조를 건드려 merge conflict와 중복 이벤트 핸들러가 생긴다. 많은 CRUD 페이지보다 좁은 두 흐름 제품이 안전하다. [내 판단]

4. AI 프로세스 관점

좋은 AI 사용 이야기:

- 규칙 기반 추천 또는 점수화: AI에 카테고리와 점수 규칙을 제안하게 한 뒤 경계 사례를 테스트한다. AI는 모호한 기준이나 일관되지 않은 가중치를 자주 내므로 “제안 → 테스트 실패 → 수정” 이야기가 분명해진다. [내 판단]

- 한국어 폼 검증과 엣지 케이스: AI 생성 코드가 빈 한국어 텍스트, 중복 입력, 날짜, 초기화 동작, localStorage 유지 처리를 잘못할 수 있다. 이런 오류는 시연과 수정이 쉽다. [내 판단]

- 데이터/API 해석: AI가 응답 필드를 지어내거나 단위를 오해하거나 누락 데이터를 잘못 다루거나 CORS로 실패하는 코드를 제안할 수 있다. 따라서 좁은 날씨 도구나 선별 데이터 도구가 강한 프로세스 이야기를 만들 수 있다. 일반 날씨 앱이 시각적으로 흔하다는 점은 그대로다. [내 판단]

- 시나리오 퀴즈 또는 의사결정 도구: AI가 모호한 질문과 겹치는 답변 규칙을 만들 수 있다. 반 친구들과 질문을 테스트하면 콘텐츠와 점수 방식을 고친 근거가 생긴다. [내 판단]

- 접근성과 반응형 동작: AI에 체크리스트를 요청한 뒤 직접 검증한다. 잘못된 ARIA 사용, 키보드 트랩, 읽기 어려운 대비, 모바일 넘침이 눈에 보이는 수정 지점이 된다. [내 판단]

한국 학교 AI 프로젝트 가이드는 AI 오류 사실 확인, 제안이 실제 환경에 맞는지 질문하기, 사용자 피드백 수집, 프로토타입 반복, 최종 결과만이 아니라 과정을 기록하기를 구체적으로 권장한다. [출처: [인천교육청 AI·디지털 활용 운영계획](https://edu-i.ice.go.kr/cmm/fms/FileDown.do?atchFileId=FILE_000000000140940&bbsId=BBSMSTR_000000004155&fileSn=1&nttId=126859&trgetId=SYSTEM_DEFAULT_BOARD)]

눈에 보이지 않게 되는 AI 사용:

- 포트폴리오, 랜딩 페이지, 클론코딩: AI가 다듬어진 마크업과 CSS를 빠르게 만들 수 있지만 수정은 대체로 제품 사고가 적은 사소한 스타일 조정에 그친다. [내 판단]

- 일반 투두 또는 계산기: AI 출력이 예측 가능하다. “AI가 이벤트 리스너를 작성했고 나는 오타를 고쳤다”는 기억에 남는 프로세스 이야기가 아니다. [내 판단]

- 방문자 카운터 또는 가짜 공개 게시판: AI가 제약상 금지된 백엔드/인증/데이터베이스 동작을 제안할 수 있다. 팀은 조언을 무시하거나 설득력 없는 로컬 시뮬레이션을 만들게 된다. [내 판단]

- 영화/도서 검색 래퍼: 흥미로운 실패 대부분이 학생 자신의 제품 결정이 아니라 API 키, 할당량, CORS, 서드파티 데이터에 관한 것이다. [내 판단]

5. 그린 플래그 / 레드 플래그 체크리스트

그린 플래그:

- [내 판단] 명확히 이름 붙인 사용자 집단 하나와 구체적 상황 하나.
- [내 판단] 완성된 루프: 입력 → 결정 → 결과 → 저장된 성찰.
- [내 판단] 하나의 공통 데이터 계약을 사용하는 독립적인 세로 흐름 2개.
- [내 판단] 반 친구 최소 3명이 5분 안에 테스트 가능.
- [내 판단] localStorage 제약이 가짜 백엔드가 아닌 의도된 이점.
- [내 판단] 예상 가능한 AI 실수 최소 1개를 테스트하고 눈에 보이게 수정 가능.
- [내 판단] 기억에 남는 시나리오 하나와 측정 가능한 개선 하나가 있는 데모.
- [내 판단] 빈 상태, 오류, 모바일, 키보드, 새로고침 상태를 시연 가능.

레드 플래그:

- [내 판단] 제목을 “My Todo”, “Weather App”, “Movie Search”, “Shopping Mall”이라고 해도 되는 상태.
- [내 판단] 핵심 가치가 유명 서비스의 외형 복사.
- [내 판단] 한 사람이 모든 상태, API, 통합 작업을 소유.
- [내 판단] 두 번째 사람의 기여가 PPT, 자산, CSS 정리뿐.
- [내 판단] 백엔드가 없는데 로그인, 공개 사용자, 실시간 채팅, 실제 카운터가 필요.
- [내 판단] AI 사용이 검증 기록 없이 “전체 페이지 생성”뿐.
- [내 판단] 대상 사용자가 왜 이 제품을 필요로 하는지 팀이 설명할 수 없음.
- [내 판단] 최종 발표가 기능만 나열하고 실패, 수정, 사용자 피드백에 따른 변경을 보여 주지 못함.
